## Source-grounded hypothesis and call-path audit

`Tape.rmsnorm` originally allocates `FloatArray(x.value.rows)` for inverse RMS scales, then references it only from a backward closure; `record { ... }` does not retain closures when `Tape(training=false)`. Hypothesis: allocate this vector only in training and preserve the forward arithmetic expression order and all training gradients. The variant changes only `val inv`, a conditional assignment, and the backward-only dereference. A faithful-method Kotlin fixture (not the full source file) was compiled and run. No change to the source file or any production file was made.

Inspected direct LM1 call sites at the pinned branch:
- `LmModel.logits` uses `Tape.rmsnorm` at each layer and at the final norm, so the target lies on LM1 inference evaluation; no evidence that it is the active Gemma/LiteRT Android pathway.
- `LmModel.nll` is used by `LmEval.segmentBits` for evaluation, not by the inspected `LmRuntime.generate` loop.
- `LmRuntime.generate` on Transformer architecture calls `LmModel.nextDistribution` every generated token, but on minGRU architecture uses `MinGruStepper` and a reusable probability array instead. R3's full-model distribution allocation reduction cannot therefore be counted as an improvement to the inspected minGRU streaming loop.
- `LmRuntime.generate` uses tokenizer `encode` and `pieceBytes` for output rather than `LmBpeTokenizer.decode`; this further limits the relevance of the rejected R5 decoder optimization to this interactive path.
These are **static, source-local relationships**, not observed device call frequencies, comprehensive codebase reachability or measured Gemma inference performance.
