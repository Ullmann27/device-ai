## Verified checkpoint identity and limitations

The live [Hugging Face revision API](https://huggingface.co/api/models/deepseek-ai/DeepSeek-V4.1-Flash-1017/revision/1bae0e1088993b9b82de08f59de5be5a34e42170?blobs=true) returned SHA `1bae0e1088993b9b82de08f59de5be5a34e42170`, **48 model safetensors shards totaling 510,296,708,312 file bytes**: 510.297 decimal GB / 475.251 GiB. This independently confirms the handoff's declared file sizes; it does not verify actual downloaded content or a serving operator's checkpoint. The pinned [tensor index](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/1bae0e1088993b9b82de08f59de5be5a34e42170/model.safetensors.index.json) lists 48 files and tensor `total_size=510286023000`, which is a different measure from file-byte total. Engram tables occur in shards 47 and 48. A file shard is a container of tensors, not an independently runnable expert.

The pinned [config](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/1bae0e1088993b9b82de08f59de5be5a34e42170/config.json) declares `DeepseekV41ForCausalLM`, FP8 quantization with FP4 experts, 40 text layers, 384 routed experts/top-6 plus one shared expert, engram tables and specialized compressed attention. Sparse activation does not remove the remaining checkpoint, and this is already mixed low precision: halving 510GB merely because a new runtime says “4-bit” is unjustified.

The official pinned [reference-inference guide](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/1bae0e1088993b9b82de08f59de5be5a34e42170/inference/README.md) documents checkpoint conversion and tensor-parallel execution (example MP=8), not a production endpoint. Its small-model self-test uses **uninitialized weights**, checking kernels/shapes rather than real-model numerics. Neither that example nor a passing self-test proves actual V4.1 serving readiness.

### V4.1-specific runtime findings

The official [SGLang cookbook](https://github.com/sgl-project/sglang/blob/main/docs/cookbook/autoregressive/DeepSeek/DeepSeek-V4_1.mdx) says V4.1 serving is preview-only; stock released `pip install sglang` cannot serve it. It requires the V4.1 tool parser; the V4 parser does not handle its DSML format. Optional `SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1` moves large engram tables to host RAM, trading HBM use for host capacity, load time and huge-page requirements. This is a specific promising offload mechanism, not removal of weights. Pin a real immutable image/runtime revision before experiments. The same source warns that bounded sliding-window replay changes numerical behavior and that batch composition is not bitwise stable.

Do not reuse headline throughput as a project measurement: the official [SGLang kernel-optimization post](https://www.sglang.io/blog/deepseek-v4.1-flash-kernel-optimization) explicitly describes its 873 tokens/s point using **simulated** speculative acceptance of 5.5 on 4×GB300 with random 4k/1k token inputs and another checkpoint revision. No such number is established for this project or the pinned 1017 checkpoint.

Petals' [own privacy/security guidance](https://github.com/bigscience-workshop/petals/wiki/Security,-privacy,-and-AI-safety) says peers may recover inputs/outputs or modify responses and gives no default output-correctness guarantee. Public-swarm activations must not be treated as anonymous or private. Trusting an operator or verifying a software repair is distinct from proving every model forward pass used the promised weights.

## Equations and honest bounds

These are engineering accounting identities/lower bounds, not empirical speed claims. All bandwidths below are useful payload bandwidth; protocol overhead, contention and execution add time.

- Transfer: `T_transfer >= W / B`. For the verified file-byte total, ideal full transfer is **11.34h at 100Mbit/s**, **1.134h at 1Gbit/s**, or **6.80min at 10Gbit/s**. At 200–400 decimal MB/s it is **42.5–21.3min**. Runpod publishes storage throughput ranges, but those are not observed checkpoint load speeds here.
- Cold request: `T_cold >= T_provision + T_fetch + T_load + T_prefill + T_decode` when phases do not overlap. Persistent storage may eliminate repeated WAN downloads, but not model loading, execution, initialization or storage charges.
- Quantized storage: `W_q ≈ sum(P_group * bits_group / 8) + scales + zero_points + nonquantized_tensors + file_overhead`. For each device: `M_needed >= resident_weights + KV_cache + activations + workspace + runtime_overhead`. Dense-transformer `2*L*S*H_KV*D*bytes` is a useful conventional K/V-cache estimate, **not a validated formula for this model's compressed/shared attention**; inspect actual cache allocation.
- Offloading: `T_token >= R_miss / B_storage` and `T_token >= R_link / B_link`; the minimum miss bytes depend on caching, selected experts and resident shared tensors. Do not assume all 510GB move every token, or that top-6/384 means all storage shrinks by 64×. Prefill can select a larger union of experts across many tokens.
- Distributed serial traversal: `T_token ≳ sum_i(compute_i + latency_i + activation_bytes_i / bandwidth_i)` without overlap. Pipelining/batching changes aggregation but cannot remove communication or missing layer coverage. Metadata alone cannot establish a public swarm's latency or availability.
- Remote request cost: `C_call = input_tokens*p_in + output_tokens*p_out + other_billable_usage`; use the provider's actual price units and include reasoning/cache/tool charges where relevant. Billed-compute cost is `rate_per_hour*(provision+fetch+load+serve+idle)_hours + storage + transfer + request charges`. “No charge to owner” requires a real operator contract/assertion, not a router flag.
- Durable storage: using the checked Runpod first-TB standard list rate, **600GB provisioned would be $42/month** (`600*$0.07`), before compute and other charges. This is a current list-price illustration; no resource was created. Requested file bytes are not the same as provisioned size or runtime/conversion scratch capacity.
- Recipe test: `pass@1 = independently_verified_first_repairs / all_heldout_tasks`; `calls_per_verified_repair = remote_calls / independently_verified_novel_repairs` (undefined at zero denominator). Also publish remote calls per task, bytes, latency, exact spend, refused/unavailable routes and retention on old tasks. A smaller denominator can falsely improve some ratios; compare at matched independent Pass@1 and protected budgets.

The [LLM-in-a-flash paper](https://arxiv.org/abs/2312.11514) reports hardware-aware flash loading for models up to roughly twice available DRAM; it is no evidence for arbitrary 510GB models on phone RAM. [FlexGen](https://arxiv.org/abs/2303.06865) targets latency-insensitive batching across GPU/CPU/disk; aggregate throughput at large batch must not be presented as single-user interactive speed. Neither establishes V4.1 compatibility.

## OneToken: intended referent UNRESOLVED

The name is ambiguous. Verified first-party candidates include [LTM BlueVerse OneToken](https://www.ltm.com/services/blueverse/blueverse-onetoken-enterprise-ai-optimization-governance), a workload-routing/governance offering, [onetoken.one](https://onetoken.one/), an API gateway/service, and [MaximeRivest/onetoken](https://github.com/MaximeRivest/onetoken), a local/remote classification library using existing model runtimes. None establishes storage-free access to the pinned checkpoint.

Search indexes also expose `onetoken-oss/K3Flight` claims about Kimi K3 CPU inference with ~55GB RAM while a ~929GB checkpoint remains on disk. **Live primary checks returned HTTP404** for the GitHub organization, repository, raw README on main/master, repository API and releases API. Current source, binaries, releases, licensing, model identity and performance therefore were not verified. Cached snippets and third-party summaries are insufficient; do not execute a purported binary or cite its figures as established. Even if later verified, that would be another model on Linux/x86, not proof for DeepSeek-V4.1 or Android. Exact user-intended OneToken URL/implementation remains required before relying on the name.

## Priority experiment and open facts

Start with **E, offline**, because it can falsify the proposed leverage without new hardware, downloads or remote disclosure. Freeze heldout task families and counterexamples; separate recipe-writing evidence from evaluation evidence; require exact precondition checks and fresh protected tests in the canonical CCC1 chain. Unknown or failed preconditions must abstain. Record failed attempts and zero-success denominators. No validated independently measured remote-call reduction is currently known.

For A–D, unresolved facts are actual authorized endpoint existence, exact runtime/image support for revision `1bae…2170`, physical hardware/available memory, bandwidth, total provisioned storage/scratch, prices/zero-charge conditions, privacy eligibility, result-verification evidence and Android execution feasibility. The next useful artifact is a metadata-only compatibility/capacity sheet, not a GPU booking or a fabricated availability flag.
