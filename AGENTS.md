## PRIORITÄT 25.10.2026: VERBINDLICHER GITHUB-FIRST-ARBEITSMODUS (Astra, Sol, alle Agenten)

**Besitzeranweisung:** Kein Agent darf neue oder reparierte Quellen, Tests, Trainingskonfigurationen oder Integrationsänderungen exklusiv in einem kurzlebigen Chat-/Research-/Cloud-Workspace halten. Das private Repository `Ullmann27/device-ai` bleibt das **offizielle, für berechtigte Mitarbeitende zugängliche System of Record**. Ein lokaler Workspace darf zum Experimentieren verwendet werden, aber **niemals als einziger Speicherort einer brauchbaren Entwicklungsarbeit**. Keine fremden geheimen Branches, nicht erreichbaren Forks oder ausschließlich in Chat-Nachrichten abgelegten Quellstände.

1. **Branch vor Arbeit:** Prüfe `HEAD`, Remote und PR-Abstammung. Arbeite auf einem explizit benannten **Branch im selben offiziellen Repository**, ausgehend vom aktuellen gemeinsam vereinbarten Integrationsstand. Nutze bei parallelen Entwicklern einen klar benannten eigenen Branch **mit sofort eröffnetem Draft-PR zum Integrationsstand**, damit niemand einen gemeinsamen Branch gegeneinander überschreibt. Ein eigener Branch im Repository ist *nicht* „versperrt“; ein nur lokal vorhandener Branch ohne Push ist es.
2. **Früher erster Push:** Erstelle vor größeren Experimenten einen sichtbaren Start-Checkpoint (gegebenenfalls Handoff/Manifest) und pushe ihn. Nach **jedem wichtigen sinnvollen Entwicklungsschritt** sofort committen und pushen; auch kleinere validierte Schritte ohne lange Ansammlung veröffentlichen. Bei längerer Arbeit einen fortsetzbaren Checkpoint spätestens etwa alle **5–10 Minuten**, wenn technisch möglich, sowie **vor** riskanten Experimenten, Kontext-/Nutzungslimitwechseln und geplanten Unterbrechungen.
3. **Tests ehrlich:** Neue ungetestete Dateien dürfen nur mit eindeutigem `WIP/UNVERIFIED`-Status im Forschungsbranch gesichert werden; niemals als abgeschlossene Reparatur ausgeben. Jeder Checkpoint nennt echte Tests, `FAILED`, `NOT_RUN`, `UNAVAILABLE`, exakte SHA und offene Blocker. Keine CI/APK-/Device-Erfolge erfinden.
4. **Pflicht-Handoff:** Pflege ein versioniertes `docs/research/omega/<AGENT>-HANDOFF.md` im **selben gepushten Branch**, inklusive Änderungen/Zweck, Komponentenverbindungen, Sicherheitsgrenzen, Testbefehlen/-ergebnissen, nächstem Einstiegspunkt, Rückfallplan. Ein weiterer Entwickler muss ohne denselben Cloud-Workspace weiterarbeiten können.
5. **GitHub-Connector statt anonymer Clone:** Das Repository bleibt `private`. Falls `git clone` in einer externen Umgebung wegen fehlender Credentials scheitert, benutze den bereits autorisierten GitHub-Connector oder einen separat genehmigten sicheren Checkout; Repository nicht öffentlich machen, keine Tokens in Chats/Logs/Quellen. Meldet der Connector Fehler, stelle den vollständigen Patch samt Tests und Dateipfaden im Chat oder als Datei zur Wiederherstellung bereit, sage aber ausdrücklich `NOT_PUSHED`.
6. **Keine verbotenen Integrationen:** Kein automatischer Merge nach `main`, keine Besitzer-APK-Signierung/Installation, kein produktiver Schlüsselwechsel; keine Umgehung von CCC1-, ToolGate-, Owner-/Tenant-Gates. Für umfangreiche Reparaturpakete eine **einmalige klar abgegrenzte Besitzer-Sammelfreigabe** einholen; plattformseitige technische Freigabedialoge nicht umgehen. Einen aktiven fremden Branch niemals per Reset/Force-Push verändern.
7. **Unterbrechungen:** Eine unvorhersehbare Prozessbeendigung kann niemand garantieren abzufangen. Deshalb sollen *vorherige* verifizierte Checkpoints bereits remote existieren. Bei wiederaufgenommener Sitzung zuerst die real gepushten Commits und Handoff-Datei lesen; nicht behaupten, ungespeicherte lokale Arbeit sei auf GitHub.

**Abnahmeregel:** „Implementiert“ ist nicht „auf GitHub gesichert“. Gib zu jedem Meilenstein die **genaue GitHub-Commit-URL** und ggf. Draft-PR an; ohne diese Belege bleibt der Status `LOCAL_ONLY / NOT_PUSHED`. Dieses Regelwerk gilt zusätzlich zu den bestehenden Experiment-/Branch-/Besitzerregeln; bei Sicherheitskonflikt gewinnt die strengere Regel.

## Nicht verhandelbares Produktziel
**Mobile-first:** Der Coding-Agent muss **direkt auf Android** programmieren, testen, eine APK bauen und nach Eigentümerbestätigung installieren können. Ein PC/Mac ist lediglich ein späterer optionaler Worker. Baue keine PC-Pflicht ein und verwechsle eine Android-Oberfläche nicht mit nachgewiesenem on-device Build.

## Regelwerk
1. Reale Ist-Schnittstellen lesen, betroffenes Experiment aus dem Register bestimmen und zukünftige Adapterfähigkeit erhalten.
2. Bevorzuge eine gemeinsame Backlog-/Repair-/Evidenz-Pipeline statt paralleler konkurrierender Lösungen; UI-Transport, native Toolchain, optionale externe Worker und KI-Kandidaten getrennt kapseln.
3. Nur erlaubte feste Toolchain-Aufgaben ausführen, keine aus Modelltext übernommene Shell. Keine ungesicherten Fremdskripte/Android-Tools aus dem Netz starten.
4. Experimentelle Änderungen isoliert, abschaltbar und durch Negative-/Holdouttests belegbar halten. Nicht verdeckt in bestätigtes Gedächtnis oder produktive Codegenerierung befördern.
5. Git-HEAD, Toolversion, APK-Hash, Tests und Gerätetests getrennt berichten. Fehlende native SDK-Werkzeuge als `UNAVAILABLE` ausgeben; keinen Erfolg erfinden.
6. Kein unkontrollierter Merge nach main, keine Installation ohne Besitzerzustimmung, keine Secrets in Repos oder APKs. Erlaubte Systemgrenzen wahren.
7. Zu jedem implementierten Schritt: Experiment-ID, Kompatibilitätsbeurteilung, Tests, nächster Schritt, Rollback protokollieren.
